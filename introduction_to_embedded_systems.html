1. Introduction and learning objectives

Definition: An embedded system is a computer-based system designed to perform a specific function, or a small set of closely related functions, as part of a larger product or machine.

Unlike a general-purpose computer, which can run many unrelated applications, an embedded system is usually designed around a particular job. It combines hardware and software, interacts with the physical world through inputs and outputs, and may need to respond within a predictable time.

Simple example: In a washing machine, the controller reads water-level and door sensors, runs the wash program, and switches the motor and valves at the right time. That controller is an embedded system.

Learning objectives

  • Define an embedded system and distinguish it from a general-purpose computer.
  • Identify its main hardware and software blocks.
  • Explain sensor-to-controller-to-actuator signal flow.
  • Understand microcontrollers, processors, memory, firmware, interrupts, and real-time constraints.
  • Compare common embedded-system types and evaluate design trade-offs.
  • Answer fundamental exam and technical interview questions.

2. Basic architecture of an embedded system

The exact architecture varies, but most embedded systems contain a processing unit, memory, input/output interfaces, firmware, and a power source. Systems connected to the physical world often include sensors and actuators.

3. Working principle: step by step

  1. Sense: A sensor detects a physical quantity such as temperature, pressure, light, or speed.
  2. Condition and convert: Signal-conditioning circuitry scales or filters the signal. An ADC converts an analog voltage into a digital number when required.
  3. Process: The CPU runs firmware and compares the measured value with the required condition.
  4. Decide: The program selects an action—for example, turn a fan on if temperature exceeds a threshold.
  5. Act: GPIO, PWM, a DAC, or a driver circuit controls the output device. A processor pin usually cannot directly drive a high-current motor.
  6. Repeat and communicate: The system samples again, updates its state, and may send status data to another device.
Control-loop example: Temperature sensor → ADC → controller compares temperature with setpoint → PWM output → fan driver → fan speed changes → temperature is measured again.

Software execution models

Super loop

Polling / main loop

Firmware repeatedly checks inputs and runs tasks. Simple and low overhead, but event response can be delayed by long tasks.

Event-driven

Interrupt-based

An interrupt signals an event such as a timer tick or received byte. The interrupt handler should usually be short and predictable.

Multitasking

RTOS-based

A scheduler runs tasks according to priority and timing rules. Useful when several activities need coordinated execution.

Real-time behavior

A real-time system is judged not only by the correctness of its result, but also by whether it produces that result within the required time. A hard real-time deadline miss may be catastrophic; a soft real-time miss degrades quality but may be tolerable. “Real-time” does not simply mean “very fast.”

ConceptMeaningExample
LatencyTime between an event and the system response.Time from a button press to a display update.
DeadlineLatest acceptable completion time.Control calculation must finish within 1 ms.
DeterminismPredictability of timing and behavior.Periodic motor-control task executes at fixed intervals.
JitterVariation in timing from one execution to another.Timer task starts at slightly different times.

DC and signal behavior

Digital input pins interpret voltage ranges as logic 0 or logic 1 according to the device's electrical specifications. Analog sensors may require an ADC. Output pins can provide logic levels, while PWM approximates a controllable average output by varying duty cycle; filtering or a suitable driver may be required for a smooth analog-like signal or a motor load.

Common architecture styles

  • Microcontroller-based: compact control with integrated peripherals.
  • DSP-based: optimized for repeated mathematical operations in audio, communications, and signal processing.
  • SoC-based: multiple subsystems integrated into one chip, often for complex connected products.
  • FPGA-based: custom parallel hardware logic for low-latency or specialized processing.

5. Design workflow and practical considerations

  1. Define requirements: functionality, timing, operating environment, safety, cost, size, and lifetime.
  2. Select hardware: MCU/MPU, memory, sensors, actuators, interfaces, clock, and power supply.
  3. Develop firmware: drivers, initialization, control logic, state machines, and error handling.
  4. Build and integrate: schematic/PCB, component drivers, communication protocols, and enclosure.
  5. Verify: unit tests, integration tests, boundary cases, timing tests, and hardware-in-the-loop tests where appropriate.
  6. Validate in the real environment: temperature, vibration, electromagnetic interference, battery life, and user behavior.
  7. Maintain securely: diagnostics, safe updates, access control, and lifecycle support.

Key design trade-offs

ConstraintQuestions to askPossible response
TimingCan every task meet its deadline under worst-case load?Optimize critical code, simplify scheduling, choose faster hardware.
PowerHow long must a battery last?Sleep modes, duty cycling, low-power peripherals.
MemoryWill code, stack, and data fit safely?Profile memory, reduce buffers, choose suitable MCU.
ReliabilityWhat happens after a sensor or software fault?Watchdog, diagnostics, safe states, fault detection.
SecurityCan an attacker alter firmware or data?Secure boot, signed updates, least privilege, protected keys.
CostCan the target price and production volume be met?Balance chip capability, external components, and manufacturing.
Common misconception: Every embedded system does not need an RTOS or an internet connection. A tiny controller can run a simple loop and still be a complete embedded system.

Common laboratory debugging checklist

  • Check supply voltage, ground, reset, clock, and pin configuration first.
  • Confirm the correct board, compiler target, linker script, and firmware image.
  • Check baud rate and wiring for serial communication; verify pull-ups for buses that require them.
  • Use an oscilloscope or logic analyzer to inspect timing and signal integrity.
  • Check interrupt priorities, shared variables, buffer limits, and race conditions.
  • Reproduce faults and test recovery paths rather than only testing the happy path.

8. Core electronics interview questions

Open each question to review a concise interview-ready answer and a possible follow-up.

1. What is an embedded system?

A computer-based system designed to perform a dedicated function within a larger product, using hardware and firmware to interact with its environment. Follow-up: Give an example such as a washing-machine controller.

2. How is an MCU different from an MPU?

An MCU commonly integrates CPU, memory, and peripherals on one chip and is well suited to control tasks. An MPU often uses external memory and is suited to more complex computing systems. The distinction is architectural, not an absolute rule.

3. What is firmware?

Low-level software stored in non-volatile memory that initializes hardware and implements device behavior. It may be bare-metal or run under an RTOS or operating system.

4. Polling vs interrupts—what is the difference?

Polling repeatedly checks whether an event has occurred. Interrupts notify the CPU when an event needs attention. Polling is simple; interrupts can improve responsiveness and reduce unnecessary checking, but require careful shared-state and latency management.

5. What is an RTOS, and when would you use one?

An RTOS schedules tasks with timing requirements and offers services such as priorities, synchronization, and timers. Use one when concurrent activities and predictable scheduling justify its complexity.

6. Why should an interrupt service routine be short?

A long ISR delays other interrupts and tasks and increases worst-case response time. Capture essential information, clear the event, and defer lengthy processing to a task or main loop.

7. What is a watchdog timer?

A hardware timer that expects periodic servicing by healthy software. If the software hangs and fails to service it, the watchdog can trigger a reset or recovery action. It must be designed so faulty code cannot blindly keep it alive.

8. Explain ADC and PWM in a sensor-control application.

An ADC converts an analog sensor voltage into a digital value. PWM controls output power by changing pulse duty cycle. A controller can sample temperature using ADC and adjust fan speed using PWM through a suitable driver.

9. How would you debug a board that does not boot?

Check power rails and current draw, reset and clock signals, boot-mode pins, programming connection, firmware image, and serial/debug output. Change one variable at a time and compare against a known-good setup.

10. What is the difference between hard and soft real-time?

In hard real-time systems, a missed deadline is unacceptable and may cause system failure. In soft real-time systems, occasional misses reduce quality but may be tolerated. Both require understanding worst-case timing.

11. Why is the volatile keyword used in embedded C?

It tells the compiler that a value may change outside the ordinary program flow, such as a memory-mapped hardware register or a variable updated by an ISR. It does not make an operation atomic or provide thread synchronization.

12. What is a memory-mapped register?

A hardware control/status register accessed through a specific address in the processor's address space. Firmware reads or writes it to configure peripherals or inspect events; access width and ordering requirements must be respected.

13. How do UART, SPI, and I²C differ?

UART is typically asynchronous point-to-point serial communication; SPI is a synchronous bus with clock and separate data lines and often a chip-select per device; I²C is a synchronous two-wire addressed bus. Selection depends on speed, wiring, distance, device support, and system needs.

14. What is a race condition?

A result that depends on the timing or order of concurrent operations on shared data. Prevent it using suitable critical sections, atomic operations, queues, or RTOS synchronization primitives.

15. How would you reduce power consumption?

Measure first; then consider sleep modes, lower clock frequency when feasible, event-driven operation, peripheral shutdown, shorter active time, and efficient radio use. Verify that timing and responsiveness requirements still pass.

10. Quick revision and formula sheet

High-priority facts

  • An embedded system combines hardware and software for a dedicated function.
  • Firmware is commonly stored in Flash/ROM; runtime variables and stack are typically in RAM.
  • MCUs integrate processor, memory, and peripherals; MPUs commonly rely on external memory and support circuitry.
  • Inputs may use GPIO or ADC; outputs may use GPIO, PWM, DAC, or communication interfaces.
  • Interrupts respond to events; an RTOS schedules tasks; a watchdog helps recover from hangs.
  • Real-time correctness includes meeting timing constraints—not merely producing the right value.
  • Design priorities often trade off performance, power, memory, cost, reliability, safety, and security.

Useful equations and conversions

Sampling interval

Ts = 1 / fs

Sampling frequency fs in hertz; interval Ts in seconds.

Ideal ADC step size

LSB ≈ Vrange / 2N

For an ideal N-bit ADC over a specified full-scale range. Exact endpoint conventions depend on the ADC definition.

PWM duty cycle

D = (TON / T) × 100%

TON is on-time; T is total period.

Execution utilization

U = C / T

For a periodic task, C is execution time and T is period. For multiple tasks, total utilization is often Σ(Cᵢ/Tᵢ), under stated scheduling assumptions.

Data rate

R = bits / time

For example, 8000 bits transmitted in 2 ms gives 4 Mbit/s average data rate.

Battery energy (approx.)

E ≈ V × Q

For roughly constant voltage V and charge capacity Q in ampere-hours, energy is in watt-hours. Real usable capacity depends on load and conditions.

Advantages and limitations

AdvantagesLimitations / challenges
Dedicated function; compact and cost-effective at scale; fast response; low-power options; can be highly reliable.Limited memory and processing in small devices; hardware-specific debugging; difficult field updates; timing complexity; security and long-term support challenges.

Common errors to avoid

  • Confusing RAM with Flash: RAM is usually volatile; Flash is non-volatile.
  • Assuming an MCU pin can directly drive a motor or relay: use an appropriate driver and protection circuit.
  • Assuming volatile makes code thread-safe: it does not.
  • Ignoring worst-case execution time and interrupt latency in a real-time design.
  • Using the wrong voltage level or forgetting common ground between interfaced circuits when required.
  • Calling every embedded device an IoT device: networking is optional.
Memory aid — “S-P-A-C-E”: Sense the environment, Process data, Act on outputs, Communicate if needed, and Ensure timing and reliability.
